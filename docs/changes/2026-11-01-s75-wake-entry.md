# S75 亮屏后恢复系统启动入口

执行者：Codex；会话：01a194f6-425e-7c00-b019-0f9761f5bdcc。

## 实机失败与根因

boot 26 的组合配置保留、隔离包进程存活，但一次较长待机后的实际唤醒仍回到小米桌面。普通待机日志记录 `gotoSleepStayAliveProcess feature disable`，没有此前的目标包强停；唤醒时小米启动页面取得前台，再调用归藏 INFO 入口。归藏记录本次 boot 已尝试，随后退出。

跳过清理只保留进程，不能阻止系统启动页面覆盖归藏。原来的完整开机去重将这次真实亮屏后的系统入口也直接跳过；仅放开全部 INFO 调用又会造成同次开机反复抢占。

## 修改

- `GuiZangApplication` 动态接收系统 OFF/ON，进程内观察到 OFF→ON 后记录一次 30 秒的恢复机会。接收器只记录状态，不启动 Activity；重复 ON 不延期，再次 OFF 清除，进程重建不从偏好恢复旧机会。
- `BootGateActivity` 保持原完整开机入口优先，并清除该次唤醒机会。完整开机应跳过时，才在入口 resumed、已解锁、可交互、开关开启且系统目标仍是本包时消费亮屏机会。没有 OFF→ON 的普通 INFO/Home 不会突破原开机去重。
- Android 14 可能延迟交付缓存进程的广播；入口在同次开机无机会时最多等待一秒重新评估，暂停/停止取消回调。不会单凭可交互状态制造亮屏机会。30 秒按广播投递的 `elapsedRealtime` 计时，不声称严格等于物理按键后的时间。
- 唤醒使用独立的 `wake-attempted`、`wake-confirmed`、来源及状态，不改完整开机的 `attempted`、`confirmed`、来源和状态。请求只记为请求，`FrameHomeActivity.onResume()` 才确认；沿用已有 `onNewIntent()` 更新 Intent 的逻辑，支持 singleTask 实例复用。
- 配置工具仅将明确的验证包 `io.github.op7418.guizangtv.s75wake` 加入 allowlist，保留未知包拒绝、设备身份核对、冲突保护及原值恢复。

恢复条件是实际亮屏后，系统已将归藏启动入口带到前台。不根据调用方包名冒充系统认证，不提供后台拉起或进程强停后的复活能力；也不推断待机前播放器或 HDMI 的恢复意图。
