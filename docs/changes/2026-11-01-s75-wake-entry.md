# S75 长待机后系统启动入口的回归测试

执行者：Codex；会话：01a194f6-425e-7c00-b019-0f9761f5bdcc。

## 新的实机失败

boot 26 的组合配置保留，归藏隔离包进程存活，但一次较长待机后的实际唤醒仍回到小米桌面：

- 普通待机路径记录 `gotoSleepStayAliveProcess feature disable`，没有先前的目标包强停。
- 唤醒时，小米桌面的启动页面取得前台，再通过 INFO 入口调用归藏。
- 归藏记录本次 boot 已尝试，随后退出，没有重新进入主界面。

这表明跳过清理只能保留进程，不能保证系统桌面在唤醒时不会覆盖归藏。现有完整开机的一次去重不区分真实亮屏后的恢复请求。

## 本次测试阶段

`BootGateFlowTest` 新增回归：当前 boot 已有 `attempted` 和 `confirmed`，应用开关开启、系统目标是本包；收到实际 OFF→ON，设备可交互且已解锁，启动入口处于 resumed 时，应请求打开 `FrameHomeActivity`。测试仅使用现有 Android/Robolectric API，不以缺少新生产方法造成的编译错误作为 RED。

Android 回归的断言失败尚待构建环境或 CI 实际运行确认，当前没有实现唤醒恢复。配置工具另有独立 RED：新隔离包 `io.github.op7418.guizangtv.s75wake` 被旧 allowlist 拒绝，apply→restore 回归得到预期的非零返回断言失败。后续只允许扩展这一个包名，保留未知包拒绝和原值恢复约束。

## 修复与验证计划

拟在进程内动态接收系统 OFF/ON，仅记录短期一次恢复机会；接收器不启动界面。只有配置仍指向本包、开关开启、已解锁、可交互且启动入口实际在前台时，才消费该机会。没有 OFF→ON 的普通 INFO/Home 调用继续遵守原开机去重；暂停、再次关屏、过期或配置失效时不得启动。

Android 14 可能延迟交付缓存进程广播，启动入口需给交付竞态一个有界等待；机会时限按广播投递时的单调时间计算，不声称等于物理按键时刻。进程重建不恢复旧机会，且不依赖调用方包名冒充系统身份。

观察到有效 Android RED 后才实现，再运行 Android 测试、lint 和构建。实机使用独立 `.s75wake` 包和仓库外固定私有调试签名，保留现有包及数据；目标切换前另建配置备份，恢复时先退回先前试用目标，再按原备份恢复最初设置。测试通过、构建成功和真实长待机回归分别报告，不相互替代。
